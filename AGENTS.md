# Developer & Agent Guidelines for VersionCheck

Этот документ описывает ключевые архитектурные правила, рабочий процесс релизов и грабли, с которыми сталкивались при разработке, чтобы будущие агенты и разработчики не наступали на них повторно.

---

## 🚀 Процесс релизов (Release Workflow)

В проекте настроен автоматический CI/CD через GitHub Actions ([`.github/workflows/release.yml`](.github/workflows/release.yml)), который срабатывает при пуше любого тега вида `v*`.

### ⚠️ Критическое правило создания релиза:
**НИКОГДА не создавать релиз вручную через `gh release create`!**
Если создать релиз локально через `gh release create`, экшен на GitHub упадет с ошибкой `HTTP 422: Release.tag_name already exists` из-за попытки создать релиз повторно.

### Чек-лист выпуска новой версии:
1. **Поднять версию**: обновить `version = "X.Y.Z"` в [`pyproject.toml`](pyproject.toml).
2. **Записать чейнджлог**: добавить секцию с новой версией в [`MEMORY.md`](MEMORY.md).
3. **Обновить примеры в документации**: если изменился список утилит или флаги, обновить актуальный вывод терминала и таблицу флагов в [`README.md`](README.md).
4. **Закоммитить и запушить в ветку main**:
   ```bash
   git add pyproject.toml MEMORY.md README.md check_versions.py
   git commit -m "feat/fix: описание изменений (vX.Y.Z)"
   git push origin main
   ```
5. **Создать и отправить тег** (релиз создаст GitHub Action):
   ```bash
   git tag vX.Y.Z
   git push origin vX.Y.Z
   ```
6. Дождаться успешного завершения GitHub Actions workflow `Release`.

## 🏗️ Архитектурные принципы

### 1. Монолитность и переносимость (Self-Contained)
* Скрипт [`check_versions.py`](check_versions.py) должен оставаться **однофайловым** (single-file), без выноса логики в сторонние bash-файлы (`.sh`).
* Проект часто запускается на удалённых серверах через SSH (`uv run - < check_versions.py`) или обновляется командой `git pull origin main`. Внешние вспомогательные файлы легко потерять при синхронизации или пересылке.
* Для выполнения кастомных апдейтов (например, для LocalSend) используется скрытый сервисный флаг самого скрипта (например, `--update-localsend`), чтобы не нарушать переносимость и сохранять единый механизм логирования через `run_and_log_subprocess`.

### 2. Кроссплатформенность (Linux & macOS)
Скрипт активно используется на нескольких устройствах — на разных дистрибутивах Linux (Fedora, Ubuntu) и macOS:
* **Linux**:
  * Портативные GUI-приложения обычно распаковываются в `~/Applications/<App>`.
  * Локальные версии Flutter-приложений часто читаются из `version.json` внутри `data/flutter_assets/version.json`.
* **macOS**:
  * Приложения лежат в `/Applications/<App>.app` или `~/Applications/<App>.app`.
  * Версия читается из `Info.plist` (`CFBundleShortVersionString`) с помощью стандартной библиотеки Python `plistlib`.
  * Обновления проверяют наличие Homebrew Cask (`brew upgrade --cask ...`) либо монтируют и копируют официальный `.dmg` через `hdiutil`.

### 3. Форматирование консольного вывода
* Ширина колонки названия утилиты зафиксирована на 15 символов в обычном режиме для идеального вертикального выравнивания двоеточий.
* В компактном режиме (`-c` / `--compact`) выравнивание отключается, а для приложений используются короткие псевдонимы из поля `short_name` (например, `agy CLI`).
* Статус игнорируемых обновлений помечается эмодзи `⏸️` (Pause).

### 4. Тихий пропуск неустановленных утилит (Silent Missing Apps)
* Если утилита отсутствует в системе (бинарник не найден через `shutil.which` или файлы приложения не существуют), она должна **тихо пропускаться** (`return None`), а не выводить ошибки вроде `❌ Command not found`.
* Скрипт используется на разных машинах с разным набором софта. Вывод должен содержать только то, что реально установлено на текущем устройстве.
